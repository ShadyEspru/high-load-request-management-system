# مخطط حالات دورة حياة الطلب
## Request Lifecycle State Diagram

يوثق هذا المجلد مخطط الحالات الخاص بدورة حياة الطلب في نظام إدارة الطلبات عالية الحمل **HLRMS**.

يوضح المخطط الحالات التي يمر بها الطلب منذ لحظة استلامه، مرورًا بالتحقق، والإدراج في الطابور، والمعالجة، وإعادة المحاولة، وحتى وصوله إلى إحدى الحالات النهائية.

## الحالات

| الحالة | الوصف |
|---|---|
| `RECEIVED` | تم استلام الطلب وإنشاء سجله الأولي. |
| `VALIDATING` | يجري التحقق من صحة بيانات الطلب. |
| `ACCEPTED` | اجتاز الطلب التحقق وأصبح مقبولًا للمعالجة. |
| `REJECTED` | رُفض الطلب بسبب عدم صحة البيانات أو عدم استيفاء شروط القبول. |
| `QUEUED` | نُشر الطلب بنجاح في طابور الرسائل المناسب. |
| `PROCESSING` | استلمت إحدى خدمات `Worker` الطلب وبدأت تنفيذه. |
| `SUCCEEDED` | اكتمل تنفيذ الطلب بنجاح وحُفظت النتيجة النهائية. |
| `FAILED` | فشلت محاولة المعالجة الحالية. هذه الحالة ليست نهائية دائمًا. |
| `RETRY_SCHEDULED` | جرى تحديد موعد محاولة جديدة بعد فشل قابل للاسترداد. |
| `DEAD_LETTERED` | تجاوز الطلب حد المحاولات أو حدث فشل غير قابل للاسترداد، فنُقل إلى `DLQ`. |
| `CANCELLED` | أُلغي الطلب قبل بدء التنفيذ الفعلي، بشرط سماح سياسة النظام بذلك. |

## الحالات النهائية

تنتهي دورة حياة الطلب عند الوصول إلى واحدة من الحالات التالية:

- `REJECTED`
- `SUCCEEDED`
- `DEAD_LETTERED`
- `CANCELLED`

أما الحالة `FAILED` فتمثل فشل محاولة تنفيذ، وقد ينتقل الطلب منها إلى `RETRY_SCHEDULED` أو إلى `DEAD_LETTERED`.

## قواعد الانتقال الأساسية

| من | إلى | الشرط أو الحدث |
|---|---|---|
| البداية | `RECEIVED` | استلام طلب جديد. |
| `RECEIVED` | `VALIDATING` | بدء التحقق من البيانات. |
| `VALIDATING` | `ACCEPTED` | البيانات صحيحة. |
| `VALIDATING` | `REJECTED` | البيانات غير صحيحة. |
| `ACCEPTED` | `QUEUED` | نجاح النشر وتأكيده من وسيط الرسائل. |
| `QUEUED` | `PROCESSING` | استهلاك الرسالة بواسطة `Worker`. |
| `PROCESSING` | `SUCCEEDED` | نجاح التنفيذ وحفظ النتيجة. |
| `PROCESSING` | `FAILED` | فشل محاولة التنفيذ. |
| `FAILED` | `RETRY_SCHEDULED` | الخطأ قابل للاسترداد ولم يُتجاوز حد المحاولات. |
| `RETRY_SCHEDULED` | `QUEUED` | انتهاء `Retry Delay` وإعادة نشر الطلب. |
| `FAILED` | `DEAD_LETTERED` | خطأ غير قابل للاسترداد أو تجاوز الحد الأقصى للمحاولات. |
| الحالات السابقة لـ`PROCESSING` | `CANCELLED` | وصول طلب إلغاء وقبوله وفق سياسة النظام. |

## المتطلبات المرتبطة

يرتبط المخطط بصورة أساسية بالمتطلبات التالية:

- `FR-006` تعيين الحالة الابتدائية للطلب.
- `FR-007` تحديث حالة الطلب.
- `FR-008` تسجيل سجل الحالات.
- `FR-009` إضافة الطلبات المقبولة إلى الطابور.
- `FR-013` معالجة الطلبات.
- `FR-016` تعيين الطلبات الناجحة.
- `FR-017` معالجة فشل التنفيذ.
- `FR-018` إعادة محاولة الطلبات الفاشلة.
- `FR-019` تحديد الحد الأقصى للمحاولات.
- `FR-020` نقل الطلبات إلى `Dead Letter Queue (DLQ)`.

> ملاحظة: الحالة `CANCELLED` موثقة ضمن دورة الحياة، لكن دعم إلغاء الطلبات يحتاج إلى متطلبات وظيفية مستقلة إذا تقرر إدراجه ضمن نطاق النسخة المنفذة من النظام.
