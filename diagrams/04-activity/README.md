## مخطط رحلة معالجة الطلب

يوضح المخطط رحلة الطلب منذ إرساله من **Client System** وحتى الوصول إلى إحدى النهايات التالية:

- رفض الطلب بالحالة `REJECTED` عند فشل التحقق من البيانات.
- قبول الطلب ووضعه في `Queue` بالحالة `QUEUED`.
- بدء المعالجة بواسطة `Worker Service` بالحالة `PROCESSING`.
- نجاح التنفيذ وتعيين الحالة `SUCCEEDED`.
- فشل التنفيذ وتعيين الحالة `FAILED`.
- جدولة إعادة المحاولة بالحالة `RETRY_SCHEDULED` عندما يكون الخطأ قابلًا للاسترداد ولم يتم تجاوز الحد الأقصى للمحاولات.
- نقل الطلب إلى `Dead Letter Queue (DLQ)` وتعيين الحالة `DEAD_LETTERED` عند تجاوز حد المحاولات أو حدوث خطأ غير قابل للاسترداد.

## مسارات النشاط الرئيسية

### 1. التحقق والقبول

يستقبل **Request API** الطلب، وينشئ `Request ID` فريدًا، ثم يحفظ الطلب بالحالة `RECEIVED` ويتحقق من صحة بياناته. ينتقل الطلب بعد ذلك إلى `ACCEPTED` أو `REJECTED` حسب نتيجة التحقق.

### 2. المعالجة غير المتزامنة

بعد قبول الطلب، يُنشر إلى **RabbitMQ** وتُحدّث حالته إلى `QUEUED`. يعيد النظام استجابة `HTTP 202 Accepted` مع `Request ID` دون انتظار انتهاء المعالجة.

### 3. التنفيذ الناجح

تستهلك **Worker Service** الرسالة، وتُحدّث حالة الطلب إلى `PROCESSING`. عند نجاح التنفيذ تُحفظ النتيجة، وتُعيّن الحالة `SUCCEEDED`، ثم يُرسل `ACK` للرسالة.

### 4. إعادة المحاولة

عند فشل التنفيذ تُعيّن الحالة `FAILED`. إذا كان الخطأ قابلًا للاسترداد وما زال عدد المحاولات أقل من الحد الأقصى، تُعيّن الحالة `RETRY_SCHEDULED`، ويُطبق `Retry Delay`، ثم يُعاد نشر الرسالة إلى `Retry Queue`.

### 5. طابور الرسائل الميتة

عندما يكون الخطأ غير قابل للاسترداد أو يتم تجاوز الحد الأقصى للمحاولات، تُنقل الرسالة إلى `Dead Letter Queue (DLQ)`، وتُعيّن حالة الطلب `DEAD_LETTERED`.

## الجهات والمسؤوليات

| الجهة | المسؤولية |
|---|---|
| النظام العميل (`Client System`) | إرسال الطلب واستلام الاستجابة الأولية. |
| واجهة الطلبات (`Request API`) | الاستقبال، إنشاء المعرف، التحقق، وتحديث الحالات الأولية. |
| قاعدة البيانات (`PostgreSQL`) | تخزين الطلب، سجل الحالات، الأخطاء، والنتيجة النهائية. |
| نظام الرسائل (`RabbitMQ`) | تمرير الرسائل عبر الطوابير الأساسية وطوابير الإعادة و`DLQ`. |
| خدمة التنفيذ (`Worker Service`) | استهلاك الرسائل وتنفيذ منطق المعالجة. |
| إدارة الإعادة (`Retry / DLQ`) | جدولة المحاولات اللاحقة والتعامل مع الرسائل غير القابلة للمعالجة. |
