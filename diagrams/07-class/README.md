# مخطط الأصناف للنموذج الأساسي
## Core Domain Class Diagram

## الأصناف الأساسية

### Request

يمثل الطلب الرئيسي داخل النظام، ويحمل بيانات العميل، ونوع الطلب، والأولوية، والحمولة، والحالة الحالية، وعدد محاولات الإعادة، والأوقات المهمة في دورة الحياة.

### RequestStatusHistory

يسجل كل انتقال في حالة الطلب، بما في ذلك الحالة السابقة والجديدة، وسبب التغيير، والجهة التي نفذته، وتوقيت التغيير. يرتبط الطلب الواحد بصفر أو أكثر من سجلات الحالة بعلاقة **Composition**.

### ProcessingAttempt

يمثل محاولة واحدة لمعالجة الطلب بواسطة Worker محدد. يحتفظ برقم المحاولة، وحالتها، ووقت البدء والانتهاء، وتصنيف الخطأ ورسالة الفشل عند وجودها. يرتبط الطلب الواحد بعدة محاولات معالجة.

### ProcessingResult

يمثل النتيجة الناتجة عن محاولة معالجة واحدة. قد يحتوي على بيانات النجاح أو رمز الخطأ والرسالة المناسبة. لكل محاولة نتيجة واحدة كحد أقصى.

### RetryPolicy

يمثل إعدادات إعادة المحاولة، مثل الحد الأقصى للمحاولات، والتأخير الابتدائي، ومعامل الزيادة، والحد الأعلى للتأخير، واستراتيجية Backoff، وأنواع الأخطاء القابلة لإعادة المحاولة.

## التعدادات

- `RequestStatus`: حالات دورة حياة الطلب المعتمدة في وثائق المشروع.
- `AttemptStatus`: الحالة الداخلية لمحاولة المعالجة.
- `BackoffStrategy`: طريقة حساب مدة الانتظار بين المحاولات.
- يستخدم `FailureType` كتصنيف للأخطاء، ويمكن تفصيل قيمه لاحقًا عند اعتماد استراتيجية معالجة الأخطاء النهائية.

## العلاقات الرئيسية

| المصدر | العلاقة | الهدف | التعددية |
|---|---|---|---|
| `Request` | Composition | `RequestStatusHistory` | `1` إلى `0..*` |
| `Request` | Composition | `ProcessingAttempt` | `1` إلى `0..*` |
| `ProcessingAttempt` | Composition | `ProcessingResult` | `1` إلى `0..1` |
| `Request` | Dependency/Association | `RetryPolicy` | سياسة اختيارية حسب نوع الطلب |

## قرارات التصميم

1. يفصل المخطط بين حالة الطلب العامة وحالة محاولة التنفيذ، لأن الطلب قد يمر بعدة محاولات قبل الوصول إلى حالة نهائية.
2. يحفظ سجل الحالات كسجلات مستقلة لضمان التتبع والمراجعة وعدم فقدان تاريخ الانتقالات.
3. توضع نتيجة التنفيذ على مستوى `ProcessingAttempt` حتى يمكن الاحتفاظ بنتيجة كل محاولة وعدم استبدال سجل المحاولات السابقة.
4. تفصل `RetryPolicy` عن `Request` للسماح باستخدام سياسات مختلفة حسب نوع الطلب أو الأولوية، وتعديل الإعدادات دون تغيير بنية الطلب.
5. أنواع البيانات والعمليات في المخطط تمثل تصميمًا مفاهيميًا أوليًا، ويمكن ضبطها أثناء تصميم قاعدة البيانات وواجهات الخدمات.
