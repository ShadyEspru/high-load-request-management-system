# مخططات التسلسل
## Sequence Diagrams

يحتوي هذا المجلد على مخططات التسلسل الخاصة برحلة الطلب في نظام إدارة الطلبات عالية الحمل
**High-Load Request Management System (HLRMS)**.

توضح المخططات ترتيب التفاعلات بين مكونات النظام منذ استقبال الطلب، ثم نشره في `RabbitMQ`، وحتى معالجته بنجاح أو إعادة محاولته أو نقله إلى `Dead Letter Queue (DLQ)`.

---

## 1. الملفات

### مخطط استقبال الطلب

- `request-submission-sequence.drawio`
- `request-submission-sequence.png`
- `request-submission-sequence.pdf`

يوضح هذا المخطط المسار المتزامن الذي يبدأ من `Client System` وينتهي بإعادة الاستجابة `202 Accepted` مع `Request ID`.

يغطي المخطط:

- استقبال الطلب عبر `Request API`.
- التحقق من صحة البيانات `Validation`.
- إنشاء سجل الطلب في `PostgreSQL`.
- الحالات `RECEIVED` و`VALIDATING` و`ACCEPTED`.
- نشر الرسالة في `RabbitMQ`.
- تحديث الحالة إلى `QUEUED`.
- المسار البديل للطلب غير الصحيح والحالة `REJECTED`.

### مخطط المعالجة غير المتزامنة

- `asynchronous-processing-sequence.drawio`
- `asynchronous-processing-sequence.png`
- `asynchronous-processing-sequence.pdf`

يوضح هذا المخطط التفاعل بين `RabbitMQ` و`Worker` وخدمة الطلبات أثناء تنفيذ الطلب.

يغطي المخطط:

- استلام الرسالة من الطابور.
- تعيين الحالة `PROCESSING`.
- تنفيذ الطلب وحفظ النتيجة.
- المسار الناجح والحالة `SUCCEEDED`.
- الفشل القابل للاسترداد والحالة `FAILED`.
- زيادة `Retry Count`.
- تعيين الحالة `RETRY_SCHEDULED`.
- تطبيق `Retry Delay` وإعادة نشر الرسالة.
- تجاوز الحد الأقصى للمحاولات.
- نقل الرسالة إلى `Dead Letter Queue (DLQ)`.
- تعيين الحالة `DEAD_LETTERED`.

---

## 2. المشاركون الرئيسيون

| المشارك | المسؤولية |
|---|---|
| النظام العميل `Client System` | إرسال الطلب واستلام الاستجابة الأولية. |
| واجهة الطلبات `Request API` | استقبال طلبات العميل وإرجاع الاستجابات. |
| خدمة الطلبات `Request Service` | إدارة الطلب وتغيير حالته وتنسيق النشر والمعالجة. |
| قاعدة البيانات `PostgreSQL` | حفظ بيانات الطلب والنتيجة وسجل الحالات. |
| وسيط الرسائل `RabbitMQ` | حفظ الرسائل وتوزيعها على وحدات التنفيذ. |
| وحدة التنفيذ `Worker` | تنفيذ منطق معالجة الطلب. |
| طابور التأخير `Retry Queue` | تأخير إعادة المحاولة وفق سياسة `Retry`. |
| طابور الرسائل الميتة `DLQ` | الاحتفاظ بالرسائل التي استنفدت محاولات المعالجة. |

## 4. ملاحظات تصميمية

1. تم فصل استقبال الطلب عن المعالجة غير المتزامنة لتجنب ازدحام مخطط واحد بالتفاصيل.
2. لا ينتظر `Client System` انتهاء تنفيذ الطلب؛ بل يحصل على `Request ID` ليستعلم عن الحالة لاحقًا.
3. لا يتم إرسال `ACK` للرسالة الأصلية قبل ضمان حفظ النتيجة أو جدولة إعادة المحاولة أو نقل الرسالة إلى `DLQ`.
4. يجب استخدام آلية موثوقة مثل `Publisher Confirm` عند نشر الرسائل في `RabbitMQ`.
5. يجب تسجيل كل انتقال للحالة ضمن سجل الحالات `Status History`.
