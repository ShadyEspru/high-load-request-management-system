# TEST-DATA.md

# Test Data Management Guidelines

**Project:** High-Load Request Management System (HLRMS)

**Version:** 1.0

**Status:** Accepted

---

# 1. Purpose

## 1.1 Overview

يحدد هذا المستند السياسة الرسمية لإدارة بيانات الاختبار (Test Data Management) في مشروع **High-Load Request Management System (HLRMS)**.

تلعب بيانات الاختبار دورًا أساسيًا في ضمان صحة وموثوقية نتائج جميع أنواع الاختبارات، بما في ذلك:

- Unit Testing
- Integration Testing
- Load Testing
- End-to-End Testing
- System Testing

وتهدف هذه الوثيقة إلى توحيد آليات إنشاء بيانات الاختبار، وإدارتها، واستخدامها، وتنظيفها، بما يضمن إمكانية إعادة تنفيذ الاختبارات والحصول على نتائج متسقة وقابلة للتكرار.

---

## 1.2 Objectives

تهدف إدارة بيانات الاختبار إلى:

- توفير بيانات واقعية وآمنة لجميع الاختبارات.
- ضمان إمكانية إعادة تنفيذ الاختبارات بنفس النتائج.
- تقليل الاعتماد على البيانات اليدوية.
- منع استخدام بيانات الإنتاج في بيئات الاختبار.
- دعم الاختبارات الآلية.
- دعم اختبارات الأداء والأحمال.
- تحسين موثوقية نتائج الاختبارات.
- تسهيل صيانة بيئة الاختبار.

---

## 1.3 Importance of Test Data

تعتمد جودة الاختبارات بشكل مباشر على جودة البيانات المستخدمة.

حتى لو كانت حالات الاختبار مكتوبة بصورة صحيحة، فإن استخدام بيانات غير مناسبة قد يؤدي إلى:

- نتائج مضللة.
- أخطاء يصعب إعادة إنتاجها.
- اختبارات غير مستقرة.
- انخفاض الثقة بنتائج الاختبار.
- اكتشاف متأخر للمشكلات.

لذلك تعد إدارة بيانات الاختبار جزءًا أساسيًا من عملية ضمان الجودة (Quality Assurance).

---

# 2. Scope

## 2.1 Included Data

تشمل هذه الوثيقة جميع أنواع بيانات الاختبار المستخدمة داخل المشروع، مثل:

- بيانات المستخدمين.
- بيانات الطلبات.
- بيانات المحافظ.
- بيانات الرسائل.
- بيانات RabbitMQ.
- بيانات Redis.
- بيانات PostgreSQL.
- بيانات المصادقة.
- بيانات الأداء.
- بيانات الأخطاء.

---

## 2.2 Excluded Data

لا تشمل هذه الوثيقة:

- بيانات الإنتاج.
- البيانات الشخصية الحقيقية.
- النسخ الاحتياطية.
- بيانات المراقبة التشغيلية.
- السجلات (Logs).

---

## 2.3 Applicable Environments

تطبق هذه السياسة على:

- Development Environment
- Testing Environment
- Integration Environment
- Performance Environment
- CI/CD Pipelines

ولا تطبق على بيئة الإنتاج.

---

# 3. Objectives of Test Data Management

## 3.1 Consistency

يجب أن تكون بيانات الاختبار متسقة بين جميع البيئات لضمان إمكانية مقارنة نتائج الاختبارات.

---

## 3.2 Repeatability

يجب أن تسمح بيانات الاختبار بإعادة تنفيذ نفس السيناريو عدة مرات مع الحصول على نفس النتائج.

---

## 3.3 Isolation

يجب ألا تؤثر بيانات أحد الاختبارات على اختبارات أخرى.

ويجب أن يمتلك كل اختبار مجموعة البيانات الخاصة به كلما أمكن ذلك.

---

## 3.4 Maintainability

يجب أن تكون بيانات الاختبار سهلة الإنشاء والتعديل والحذف دون الحاجة إلى تدخل يدوي كبير.

---

# 4. Test Data Principles

## 4.1 Deterministic Data

يفضل استخدام بيانات ثابتة (Deterministic Data) بحيث تكون نتائج الاختبارات قابلة للتوقع.

---

## 4.2 Independent Data

يجب ألا تعتمد حالة اختبار على البيانات الناتجة عن اختبار سابق.

كل اختبار يجب أن يكون مستقلاً.

---

## 4.3 Minimal Data

ينصح باستخدام أقل كمية ممكنة من البيانات اللازمة لتنفيذ السيناريو.

فكلما زادت البيانات دون حاجة، ازدادت صعوبة صيانة الاختبارات.

---

## 4.4 Representative Data

يجب أن تمثل بيانات الاختبار السيناريوهات الواقعية التي قد تواجه النظام في بيئة التشغيل.

---

# 5. Test Data Classification

## 5.1 Overview

تصنف بيانات الاختبار وفق الغرض من استخدامها.

---

## 5.2 Functional Data

تستخدم للتحقق من صحة الوظائف الأساسية للنظام.

أمثلة:

- مستخدم صالح.
- طلب صالح.
- محفظة نشطة.
- عملية ناجحة.

---

## 5.3 Invalid Data

تستخدم لاختبار التحقق من صحة المدخلات.

أمثلة:

- قيم فارغة.
- قيم غير صالحة.
- تنسيقات خاطئة.
- بيانات مفقودة.

---

## 5.4 Performance Data

تستخدم لمحاكاة أحجام البيانات الكبيرة أثناء اختبارات الأداء.

وقد تشمل:

- آلاف المستخدمين.
- ملايين الطلبات.
- أعداد كبيرة من الرسائل.
- قواعد بيانات ضخمة.

---

## 5.5 Security Data

تستخدم لاختبار آليات الأمان مثل:

- صلاحيات المستخدمين.
- Tokens غير صالحة.
- بيانات اعتماد منتهية.
- محاولات الوصول غير المصرح بها.

---

# 6. Data Sources

## 6.1 Synthetic Data

تعتمد معظم الاختبارات على بيانات يتم إنشاؤها خصيصًا للاختبار.

وتعد هذه الطريقة المفضلة في المشروع.

---

## 6.2 Generated Data

يمكن إنشاء البيانات آليًا باستخدام:

- Seed Scripts
- Test Builders
- Factory Classes
- SQL Scripts

---

## 6.3 Static Data

بعض الاختبارات تعتمد على بيانات ثابتة محفوظة داخل ملفات أو سكربتات لضمان ثبات النتائج.

---

## 6.4 Random Data

يمكن استخدام بيانات عشوائية عند اختبار السيناريوهات العامة، مع الحرص على أن تبقى النتائج قابلة للتحليل وإعادة الإنتاج.

---

# 7. Data Generation

## 7.1 Purpose

يجب إنشاء بيانات الاختبار بصورة آلية كلما أمكن ذلك لتقليل الأخطاء البشرية.

---

## 7.2 Automation

يفضل إنشاء البيانات باستخدام أدوات أو سكربتات قابلة لإعادة التشغيل داخل بيئة الاختبار.

---

## 7.3 Unique Data

يجب أن تكون القيم التي تتطلب التفرد (Uniqueness) مثل البريد الإلكتروني أو رقم الطلب فريدة لتجنب تعارض البيانات.

---

## 7.4 Lifecycle

تمر بيانات الاختبار بالمراحل التالية:

```text
Generate

↓

Validate

↓

Use

↓

Verify

↓

Cleanup
```

---

# 8. Synthetic Test Data

## 8.1 Overview

تعتمد HLRMS بصورة أساسية على البيانات الاصطناعية (Synthetic Data) بدلاً من استخدام بيانات حقيقية.

---

## 8.2 Benefits

توفر البيانات الاصطناعية المزايا التالية:

- حماية الخصوصية.
- سهولة الإنشاء.
- سهولة الحذف.
- سهولة إعادة الاستخدام.
- دعم الاختبارات الآلية.
- تقليل المخاطر القانونية.

---

## 8.3 Quality Requirements

يجب أن تحقق البيانات الاصطناعية الخصائص التالية:

- واقعية.
- متسقة.
- قابلة للتوسع.
- متنوعة.
- قابلة للتكرار.

---

## 8.4 Validation

يجب التحقق من صحة البيانات الاصطناعية قبل استخدامها في الاختبارات لضمان توافقها مع قواعد النظام وقيود قاعدة البيانات.

---

# 9. Database Test Data

## 9.1 Purpose

تمثل قاعدة البيانات المصدر الرئيسي للبيانات في النظام، لذلك يجب أن تكون بيانات الاختبار المخزنة في PostgreSQL مصممة بعناية لتغطية جميع السيناريوهات الوظيفية وغير الوظيفية.

---

## 9.2 Test Entities

تشمل البيانات الأساسية المستخدمة في الاختبارات:

- Users
- Wallets
- Requests
- Transactions
- Outbox Events
- Roles
- Permissions

ويجب أن تغطي العلاقات بين هذه الكيانات مختلف حالات الاستخدام.

---

## 9.3 Referential Integrity

يجب أن تحترم جميع بيانات الاختبار قيود قاعدة البيانات، مثل:

- Primary Keys
- Foreign Keys
- Unique Constraints
- Check Constraints
- NOT NULL Constraints

لضمان أن نتائج الاختبارات تعكس سلوك النظام الحقيقي.

---

## 9.4 Database State

يجب أن تبدأ كل حالة اختبار من حالة معروفة وثابتة لقاعدة البيانات، سواء عن طريق إعادة تهيئة البيانات أو تنفيذ سكربتات Seed قبل بدء الاختبار.

---

# 10. RabbitMQ Test Data

## 10.1 Purpose

تعتمد HLRMS على RabbitMQ لمعالجة الرسائل بصورة غير متزامنة، لذلك يجب توفير رسائل اختبار تمثل مختلف السيناريوهات المتوقعة.

---

## 10.2 Message Types

تشمل رسائل الاختبار:

- Create Request Events
- Update Events
- Notification Events
- Retry Events
- Dead Letter Events

---

## 10.3 Message Validation

يجب التأكد من أن جميع الرسائل:

- تحتوي على البنية الصحيحة.
- تتوافق مع مخطط الرسالة (Schema).
- تحتوي على جميع الحقول الإلزامية.
- تستخدم تنسيقات بيانات صحيحة.

---

## 10.4 Queue State

قبل تنفيذ كل اختبار يجب التأكد من أن قوائم الانتظار (Queues) في الحالة المتوقعة، مع إزالة الرسائل المتبقية من اختبارات سابقة إذا لزم الأمر.

---

# 11. Redis Test Data

## 11.1 Purpose

يستخدم Redis في المشروع كطبقة تخزين مؤقت (Caching Layer)، ولذلك يجب إدارة بياناته بصورة مستقلة عن قاعدة البيانات.

---

## 11.2 Cached Objects

قد تتضمن بيانات Redis:

- User Sessions
- Authentication Tokens
- Frequently Accessed Data
- Rate Limiting Counters
- Temporary Request Data

---

## 11.3 Cache Consistency

يجب أن تعكس البيانات المخزنة في Redis الحالة الفعلية للنظام، وألا تحتوي على بيانات منتهية الصلاحية أو غير متزامنة مع قاعدة البيانات.

---

## 11.4 Cache Cleanup

ينصح بمسح البيانات المؤقتة في Redis قبل تنفيذ الاختبارات التي تعتمد على حالة Cache محددة، لضمان نتائج قابلة للتكرار.

---

# 12. API Test Data

## 12.1 Purpose

تشمل بيانات API جميع الطلبات والاستجابات المستخدمة أثناء اختبار واجهات REST.

---

## 12.2 Request Data

يجب أن تغطي بيانات الطلبات:

- البيانات الصحيحة.
- البيانات غير الصالحة.
- الحقول الاختيارية.
- الحقول الإلزامية.
- القيم الحدية.
- الطلبات المكررة.

---

## 12.3 Response Data

يجب التحقق من:

- رموز HTTP.
- جسم الاستجابة.
- رسائل الخطأ.
- رؤوس HTTP (Headers).
- زمن الاستجابة.

---

## 12.4 Data Consistency

يجب أن تكون البيانات المرسلة إلى API متوافقة مع قواعد العمل (Business Rules) المطبقة داخل النظام.

---

# 13. Authentication Test Data

## 13.1 Purpose

تهدف بيانات المصادقة إلى اختبار جميع السيناريوهات المتعلقة بالتحقق من هوية المستخدمين وصلاحياتهم.

---

## 13.2 User Categories

ينصح بتوفير بيانات لمستخدمين يمثلون أدوارًا مختلفة داخل النظام، بما يتوافق مع نموذج الصلاحيات المعتمد.

---

## 13.3 Token Scenarios

تشمل بيانات الاختبار:

- Access Token صالح.
- Access Token منتهي الصلاحية.
- Token غير صالح.
- Token معدل.
- Token مفقود.

---

## 13.4 Authorization Testing

يجب اختبار صلاحيات الوصول باستخدام بيانات تمثل حالات السماح والمنع، للتحقق من تطبيق سياسات التحكم بالوصول بصورة صحيحة.

---

# 14. Validation Test Data

## 14.1 Purpose

تستخدم هذه البيانات لاختبار جميع قواعد التحقق من صحة المدخلات (Input Validation).

---

## 14.2 Validation Categories

تشمل:

- Required Fields
- Length Validation
- Format Validation
- Numeric Validation
- Date Validation
- Enum Validation

---

## 14.3 Invalid Inputs

يجب توفير بيانات تمثل:

- قيم فارغة.
- قيم Null.
- أحرف غير متوقعة.
- بيانات طويلة جدًا.
- بيانات قصيرة جدًا.
- تنسيقات غير صحيحة.

---

## 14.4 Expected Behaviour

يجب أن تؤدي البيانات غير الصالحة إلى رسائل خطأ واضحة، مع عدم التأثير على استقرار النظام أو سلامة البيانات.

---

# 15. Boundary Value Test Data

## 15.1 Purpose

تستخدم بيانات الحدود (Boundary Values) للتحقق من سلوك النظام عند الحدود الدنيا والعليا للمدخلات.

---

## 15.2 Boundary Categories

تشمل القيم:

- الحد الأدنى.
- أقل من الحد الأدنى.
- الحد الأعلى.
- أكبر من الحد الأعلى.

---

## 15.3 Examples

من الأمثلة:

- أصغر طول مسموح للنص.
- أكبر طول مسموح.
- أصغر قيمة رقمية.
- أكبر قيمة رقمية.
- أول تاريخ مسموح.
- آخر تاريخ مسموح.

---

## 15.4 Importance

تعد اختبارات Boundary Values من أكثر الاختبارات قدرة على اكتشاف الأخطاء الناتجة عن التحقق غير الصحيح من المدخلات.

---

# 16. Negative Test Data

## 16.1 Purpose

تهدف البيانات السلبية (Negative Test Data) إلى التحقق من قدرة النظام على التعامل مع الحالات غير الصحيحة أو غير المتوقعة.

---

## 16.2 Negative Scenarios

تشمل:

- بيانات ناقصة.
- بيانات متعارضة.
- معرفات غير موجودة.
- مراجع مكسورة.
- قيم غير منطقية.
- بيانات تالفة.

---

## 16.3 Error Verification

يجب التأكد من أن النظام:

- يعيد رمز HTTP مناسب.
- يعرض رسالة خطأ واضحة.
- لا يتسبب في انهيار الخدمة.
- لا يخزن بيانات غير صحيحة.
- لا يترك النظام في حالة غير متسقة.

---

## 16.4 Logging

يجب تسجيل الأخطاء الناتجة عن البيانات السلبية في سجلات النظام بما يكفي لتسهيل عملية التشخيص، مع تجنب تسجيل معلومات حساسة.

---

# 17. Load Testing Data

## 17.1 Purpose

تتطلب اختبارات الأداء والأحمال (Load Testing) مجموعات بيانات كبيرة تحاكي بيئة التشغيل الحقيقية، وذلك لقياس قدرة النظام على معالجة عدد كبير من الطلبات المتزامنة دون التأثير على استقرار الخدمات.

---

## 17.2 Dataset Size

يجب أن تكون بيانات اختبارات الأداء أكبر بكثير من البيانات المستخدمة في الاختبارات الوظيفية.

قد تشمل:

- آلاف المستخدمين.
- عشرات الآلاف من الطلبات.
- ملايين السجلات.
- آلاف الرسائل داخل RabbitMQ.
- كميات كبيرة من البيانات المخزنة مؤقتًا في Redis.

---

## 17.3 Data Distribution

ينبغي أن تعكس البيانات توزيع الاستخدام الحقيقي للنظام، بحيث لا تتركز جميع العمليات على نوع واحد من الطلبات أو على مستخدم واحد فقط.

ويفضل توزيع البيانات بين:

- مستخدمين جدد.
- مستخدمين نشطين.
- مستخدمين قليلـي النشاط.
- طلبات حديثة.
- طلبات قديمة.
- حالات معالجة مختلفة.

---

## 17.4 Performance Consistency

يجب أن تبقى بيانات اختبارات الأداء ثابتة طوال مدة الاختبار، وألا يتم تعديلها يدويًا أثناء تنفيذ سيناريوهات الحمل.

---

# 18. Concurrency Test Data

## 18.1 Purpose

تهدف بيانات اختبارات التزامن إلى التحقق من قدرة النظام على التعامل مع العمليات المتزامنة دون حدوث تعارض أو فقدان للبيانات.

---

## 18.2 Concurrent Scenarios

تشمل السيناريوهات:

- عدة مستخدمين ينشئون طلبات في الوقت نفسه.
- عدة Workers تعالج الرسائل بالتوازي.
- عمليات قراءة وكتابة متزامنة.
- طلبات متكررة على نفس المورد.

---

## 18.3 Shared Resources

يجب توفير بيانات تسمح باختبار الموارد المشتركة مثل:

- المحافظ.
- الطلبات.
- السجلات المشتركة.
- العدادات.
- بيانات التخزين المؤقت.

---

## 18.4 Expected Behaviour

يجب أن تؤدي العمليات المتزامنة إلى نتائج صحيحة ومتسقة، مع منع حدوث:

- Race Conditions.
- Lost Updates.
- Dirty Reads.
- Duplicate Processing.

---

# 19. Retry Scenario Data

## 19.1 Purpose

تستخدم هذه البيانات لاختبار آليات إعادة المحاولة (Retry Mechanism) عند فشل معالجة الطلبات أو الرسائل.

---

## 19.2 Retry Cases

تشمل حالات الاختبار:

- فشل مؤقت في قاعدة البيانات.
- انقطاع الاتصال بـ RabbitMQ.
- انتهاء مهلة الاتصال (Timeout).
- أخطاء الشبكة.
- تعطل خدمة خارجية.

---

## 19.3 Retry Verification

يجب أن تسمح بيانات الاختبار بالتحقق من:

- عدد مرات إعادة المحاولة.
- الفاصل الزمني بين المحاولات.
- نجاح العملية بعد إعادة المحاولة.
- انتقال الرسائل إلى Dead Letter Queue عند استنفاد جميع المحاولات.

---

## 19.4 Data Integrity

يجب ألا تؤدي إعادة المحاولة إلى:

- إنشاء بيانات مكررة.
- فقدان البيانات.
- تنفيذ العملية أكثر من مرة دون مبرر.

---

# 20. Dead Letter Queue Test Data

## 20.1 Purpose

تهدف هذه البيانات إلى اختبار الرسائل التي يتعذر معالجتها ونقلها إلى Dead Letter Queue (DLQ).

---

## 20.2 DLQ Scenarios

تشمل السيناريوهات:

- رسائل غير صالحة.
- رسائل تالفة.
- رسائل تفتقد حقولًا إلزامية.
- رسائل تتجاوز الحد الأقصى لإعادة المحاولة.

---

## 20.3 Verification

يجب التأكد من:

- انتقال الرسائل إلى DLQ.
- تسجيل سبب الفشل.
- إمكانية تحليل الرسائل لاحقًا.
- عدم فقدان الرسائل أثناء النقل.

---

## 20.4 Cleanup

بعد انتهاء الاختبارات يجب تنظيف محتويات DLQ أو إعادة تهيئتها قبل تنفيذ سيناريو جديد.

---

# 21. Test Data Cleanup Strategy

## 21.1 Purpose

بعد انتهاء الاختبارات يجب إزالة البيانات المؤقتة لضمان أن تبدأ الاختبارات اللاحقة من بيئة نظيفة ومعروفة.

---

## 21.2 Cleanup Scope

تشمل عملية التنظيف:

- جداول قاعدة البيانات.
- Redis Cache.
- RabbitMQ Queues.
- ملفات مؤقتة.
- سجلات الاختبار عند الحاجة.

---

## 21.3 Cleanup Methods

يمكن تنفيذ التنظيف باستخدام:

- SQL Scripts.
- Testcontainers Lifecycle.
- Docker Volume Reset.
- Redis Flush.
- Queue Purge.

---

## 21.4 Verification

بعد التنظيف يجب التحقق من أن البيئة أصبحت جاهزة لتنفيذ الاختبارات التالية دون أي بيانات متبقية.

---

# 22. Test Data Refresh Strategy

## 22.1 Purpose

قد تتطلب بعض الاختبارات إعادة إنشاء بيانات الاختبار بالكامل قبل كل تشغيل لضمان ثبات النتائج.

---

## 22.2 Refresh Frequency

يعتمد معدل إعادة إنشاء البيانات على نوع الاختبار، وقد يتم قبل:

- كل Test Case.
- كل Test Suite.
- كل Pipeline.
- كل إصدار جديد.

---

## 22.3 Automated Refresh

ينصح بأتمتة عملية إعادة إنشاء البيانات داخل خطوط CI/CD لتقليل التدخل اليدوي وضمان الاتساق.

---

## 22.4 Version Control

يجب حفظ جميع سكربتات إنشاء البيانات وإعادة تهيئتها ضمن مستودع المشروع، مع تتبع التغييرات عليها باستخدام Git.

---

# 23. Test Data Builders

## 23.1 Purpose

تستخدم Test Data Builders لإنشاء كائنات اختبار بصورة مرنة وقابلة لإعادة الاستخدام داخل اختبارات Unit وIntegration.

---

## 23.2 Builder Pattern

يفضل استخدام نمط Builder لإنشاء بيانات الاختبار، لما يوفره من وضوح وسهولة في تخصيص الحقول المطلوبة لكل سيناريو.

---

## 23.3 Benefits

تشمل فوائد استخدام Builders:

- تقليل تكرار الكود.
- تحسين قابلية القراءة.
- تسهيل صيانة الاختبارات.
- إنشاء بيانات متسقة.

---

## 23.4 Organization

ينصح بوضع جميع Test Data Builders في حزمة مستقلة داخل المشروع، مع تسمية واضحة تعبر عن الكيان الذي يتم إنشاؤه.

---

# 24. Seed Scripts

## 24.1 Purpose

تستخدم Seed Scripts لإنشاء بيانات أساسية يمكن الاعتماد عليها عند تشغيل النظام أو تنفيذ الاختبارات.

---

## 24.2 Seed Content

قد تتضمن:

- المستخدمين الافتراضيين.
- الأدوار والصلاحيات.
- بيانات مرجعية.
- إعدادات النظام.
- بيانات أولية للتجارب.

---

## 24.3 Idempotency

يجب تصميم جميع Seed Scripts بحيث يمكن تشغيلها أكثر من مرة دون إنشاء بيانات مكررة أو التسبب في تعارضات.

---

## 24.4 Maintenance

يجب تحديث Seed Scripts مع أي تغيير في نموذج البيانات (Data Model)، لضمان توافقها مع الإصدارات الجديدة من النظام.

---

# 25. Test Data Isolation

## 25.1 Purpose

يعد عزل بيانات الاختبار (Test Data Isolation) من المبادئ الأساسية لضمان استقلالية الاختبارات ومنع تأثير نتائج أحد الاختبارات على الاختبارات الأخرى.

---

## 25.2 Isolation Principles

يجب الالتزام بالمبادئ التالية:

- كل اختبار يمتلك بياناته الخاصة.
- لا يعتمد أي اختبار على نتائج اختبار سابق.
- لا يتم مشاركة البيانات القابلة للتعديل بين الاختبارات.
- يمكن تشغيل الاختبارات بأي ترتيب دون تغيير النتائج.

---

## 25.3 Environment Isolation

يجب عزل بيانات الاختبار بين البيئات المختلفة:

- Development
- Integration
- Performance
- CI/CD

ولا يجوز مشاركة قواعد البيانات أو قوائم الانتظار أو ذاكرة Redis بين هذه البيئات.

---

## 25.4 Parallel Execution

عند تشغيل الاختبارات بصورة متوازية، يجب التأكد من أن كل اختبار يستخدم بيانات مستقلة أو معرفات فريدة لمنع حدوث تعارضات.

---

# 26. Sensitive Data Policy

## 26.1 Purpose

تهدف هذه السياسة إلى حماية المعلومات الحساسة أثناء تنفيذ الاختبارات.

---

## 26.2 Restricted Data

يمنع استخدام:

- بيانات المستخدمين الحقيقيين.
- كلمات المرور الحقيقية.
- مفاتيح API الخاصة بالإنتاج.
- رموز الوصول (Production Tokens).
- البيانات الشخصية.
- المعلومات المالية الحقيقية.

---

## 26.3 Data Masking

عند الحاجة لاستخدام بيانات مستمدة من الإنتاج، يجب إخفاء أو استبدال جميع المعلومات الحساسة باستخدام تقنيات Data Masking أو Anonymization.

---

## 26.4 Compliance

يجب أن تتوافق جميع بيانات الاختبار مع سياسات أمن المعلومات والمتطلبات القانونية المعتمدة داخل المؤسسة.

---

# 27. Best Practices

ينصح فريق التطوير بالالتزام بالممارسات التالية:

- إنشاء بيانات الاختبار بصورة آلية.
- استخدام بيانات اصطناعية بدلًا من بيانات الإنتاج.
- جعل جميع البيانات قابلة لإعادة الإنشاء.
- استخدام Seed Scripts.
- استخدام Test Data Builders.
- تنظيف البيئة بعد انتهاء الاختبارات.
- توثيق جميع مصادر البيانات.
- مراجعة بيانات الاختبار دوريًا.
- استخدام معرفات فريدة عند الحاجة.
- أتمتة إدارة بيانات الاختبار داخل خطوط CI/CD.

---

# 28. Common Anti-Patterns

ينبغي تجنب الممارسات التالية:

- استخدام بيانات الإنتاج في بيئة الاختبار.
- مشاركة البيانات بين الاختبارات.
- الاعتماد على ترتيب تنفيذ الاختبارات.
- إنشاء بيانات يدويًا لكل اختبار.
- استخدام بيانات عشوائية غير قابلة لإعادة الإنتاج.
- عدم تنظيف قاعدة البيانات بعد الاختبارات.
- ترك الرسائل داخل RabbitMQ بعد انتهاء الاختبارات.
- ترك بيانات Redis المؤقتة دون حذف.
- تكرار نفس البيانات في عدة ملفات.
- عدم توثيق مصادر بيانات الاختبار.

# 30. Summary

تمثل إدارة بيانات الاختبار عنصرًا أساسيًا في نجاح جميع أنواع الاختبارات داخل مشروع **High-Load Request Management System (HLRMS)**.

حددت هذه الوثيقة المبادئ والسياسات الخاصة بإنشاء بيانات الاختبار، وتصنيفها، وإدارتها، وتنظيفها، وإعادة استخدامها، مع توضيح آليات التعامل مع بيانات قواعد البيانات، وRabbitMQ، وRedis، واختبارات الأداء، واختبارات التزامن، وبيانات المصادقة.

يساعد الالتزام بالإرشادات الواردة في هذه الوثيقة على ضمان أن تكون جميع الاختبارات قابلة للتكرار، ومستقرة، وتعكس سلوك النظام الحقيقي، مع الحفاظ على أمن البيانات وسهولة صيانة بيئة الاختبار.

وتعد هذه الوثيقة المرجع الرسمي لإدارة بيانات الاختبار في مشروع HLRMS.
