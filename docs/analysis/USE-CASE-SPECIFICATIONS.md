# مواصفات حالات الاستخدام  
## Use Case Specifications

## 1. مقدمة

توضح هذه الوثيقة المواصفات التفصيلية لحالات الاستخدام الخاصة بنظام إدارة الطلبات عالية الحمل  
High-Load Request Management System (HLRMS).

تهدف الوثيقة إلى شرح كيفية تفاعل الجهات الخارجية (Actors) مع النظام، وتحديد التدفق الأساسي، والحالات البديلة، والشروط المسبقة، والنتائج النهائية لكل حالة استخدام.

يرتبط كل Use Case بواحد أو أكثر من المتطلبات الوظيفية الموجودة في وثيقة:

`FUNCTIONAL-REQUIREMENTS.md`

---

# 2. الجهات المتفاعلة

| الرمز | Actor | الوصف |
|---|---|---|
| ACT-01 | النظام العميل (Client System) | تطبيق أو نظام خارجي يستخدم واجهات HLRMS لإرسال الطلبات والاستعلام عنها. |
| ACT-02 | مسؤول النظام (System Administrator) | المستخدم المسؤول عن مراقبة النظام وإدارة الإعدادات ومتابعة الأعطال. |
| ACT-03 | منصة المراقبة (Monitoring Platform) | منصة خارجية تجمع مؤشرات الأداء والحالة الصحية للخدمات. |

# 3. UC-001 – إرسال طلب جديد  
## Submit Request

| الحقل | القيمة |
|---|---|
| المعرف | UC-001 |
| الاسم | إرسال طلب جديد (Submit Request) |
| Actor الأساسي | النظام العميل (Client System) |
| الهدف | إرسال طلب جديد إلى HLRMS ليتم قبوله ومعالجته بصورة غير متزامنة. |
| المتطلبات المرتبطة | FR-001 إلى FR-005، FR-009 |
| الأولوية | عالية |

## الشروط المسبقة

1. يجب أن يمتلك النظام العميل صلاحية الوصول إلى واجهة API.
2. يجب أن تكون خدمة استقبال الطلبات متاحة.
3. يجب أن تكون بيانات الطلب بصيغة مدعومة.

## المحفز

يرسل النظام العميل طلبًا جديدًا إلى HLRMS.

## التدفق الأساسي

1. يرسل Client System بيانات الطلب إلى النظام.
2. يستقبل النظام الطلب.
3. ينشئ النظام Request ID فريدًا.
4. يخزن النظام بيانات الطلب الأولية.
5. يغيّر النظام حالة الطلب إلى `RECEIVED`.
6. يتحقق النظام من صحة البيانات.
7. يغيّر النظام الحالة إلى `VALIDATING`.
8. يقبل النظام الطلب إذا كانت البيانات صحيحة.
9. يغيّر النظام الحالة إلى `ACCEPTED`.
10. يرسل النظام الطلب إلى Queue مناسبة.
11. يغيّر النظام الحالة إلى `QUEUED`.
12. يعيد النظام استجابة أولية تحتوي على Request ID والحالة الحالية.

## التدفقات البديلة

### A1 – بيانات الطلب غير صحيحة

1. يكتشف النظام وجود بيانات مفقودة أو غير صحيحة.
2. يغيّر النظام حالة الطلب إلى `REJECTED`.
3. يعيد النظام رسالة خطأ توضّح سبب الرفض.
4. تنتهي حالة الاستخدام.

### A2 – النظام العميل غير مصرح له

1. يفشل التحقق من هوية النظام العميل أو صلاحياته.
2. يرفض النظام الطلب.
3. يعيد استجابة مناسبة دون إنشاء طلب جديد.

### A3 – تعذر تخزين الطلب

1. يفشل النظام في حفظ بيانات الطلب.
2. لا يعتبر الطلب مقبولًا.
3. يعيد النظام رسالة خطأ داخلية مناسبة.
4. يسجل النظام تفاصيل الخطأ.

### A4 – تعذر إرسال الطلب إلى Queue

1. يتم تخزين الطلب وقبوله.
2. يفشل إرسال الرسالة مؤقتًا إلى Queue.
3. يحتفظ النظام بالطلب في حالة تسمح بإعادة محاولة النشر.
4. يسجل النظام الخطأ للمراجعة.

## الشروط اللاحقة

### عند النجاح

- يكون للطلب Request ID فريد.
- تكون بيانات الطلب محفوظة.
- تكون الحالة `QUEUED`.
- يكون الطلب جاهزًا للمعالجة.

### عند الفشل

- لا يتم تنفيذ طلب غير صالح.
- يتم تسجيل سبب الخطأ أو الرفض.
- لا تُفقد البيانات المقبولة سابقًا.

# 4. UC-002 – الاستعلام عن حالة الطلب  
## Check Request Status

| الحقل | القيمة |
|---|---|
| المعرف | UC-002 |
| الاسم | الاستعلام عن حالة الطلب (Check Request Status) |
| Actor الأساسي | النظام العميل (Client System) |
| الهدف | معرفة الحالة الحالية لطلب سبق إرساله. |
| المتطلبات المرتبطة | FR-021 |
| الأولوية | عالية |

## الشروط المسبقة

1. يجب أن يمتلك النظام العميل Request ID صالحًا.
2. يجب أن يكون النظام العميل مصرحًا له بعرض الطلب.

## المحفز

يرسل Client System طلبًا للاستعلام عن حالة Request محددة.

## التدفق الأساسي

1. يرسل النظام العميل Request ID.
2. يتحقق النظام من صحة Request ID.
3. يبحث النظام عن الطلب.
4. يتحقق النظام من صلاحية الوصول.
5. يسترجع النظام الحالة الحالية.
6. يعيد النظام معلومات الحالة إلى النظام العميل.

## التدفقات البديلة

### A1 – Request ID غير موجود

1. لا يجد النظام طلبًا مطابقًا.
2. يعيد النظام رسالة تفيد بأن الطلب غير موجود.

### A2 – الوصول غير مصرح به

1. يكون الطلب موجودًا.
2. لا يمتلك النظام العميل صلاحية عرضه.
3. يرفض النظام العملية.

## الشروط اللاحقة

- لا تتغير بيانات الطلب.
- يحصل النظام العميل على الحالة الحالية عند نجاح العملية.

# 5. UC-003 – عرض تفاصيل الطلب  
## View Request Details

| الحقل | القيمة |
|---|---|
| المعرف | UC-003 |
| الاسم | عرض تفاصيل الطلب (View Request Details) |
| Actor الأساسي | النظام العميل (Client System) |
| Actor الثانوي | مسؤول النظام (System Administrator) |
| الهدف | عرض بيانات الطلب وحالته ونتيجة معالجته وسجل تغير حالاته. |
| المتطلبات المرتبطة | FR-008، FR-022 |
| الأولوية | متوسطة |

## الشروط المسبقة

1. يجب أن يكون الطلب موجودًا.
2. يجب أن يمتلك Actor صلاحية عرض الطلب.

## التدفق الأساسي

1. يرسل Actor معرف الطلب.
2. يتحقق النظام من وجود الطلب.
3. يتحقق النظام من الصلاحيات.
4. يسترجع النظام بيانات الطلب.
5. يسترجع النظام الحالة الحالية.
6. يسترجع النظام سجل الحالات.
7. يسترجع النظام نتيجة المعالجة إذا كانت متاحة.
8. يعرض النظام التفاصيل المطلوبة.

## التدفقات البديلة

### A1 – الطلب غير موجود

يعيد النظام رسالة تفيد بعدم وجود الطلب.

### A2 – النتيجة غير جاهزة

يعرض النظام تفاصيل الطلب والحالة الحالية دون نتيجة نهائية.

### A3 – الوصول غير مصرح به

يرفض النظام العملية ولا يعرض بيانات الطلب.

## الشروط اللاحقة

- لا تتغير بيانات الطلب.
- يتم عرض التفاصيل المصرح بها فقط.

# 6. UC-004 – البحث في الطلبات  
## Search Requests

| الحقل | القيمة |
|---|---|
| المعرف | UC-004 |
| الاسم | البحث في الطلبات (Search Requests) |
| Actor الأساسي | النظام العميل (Client System) |
| Actor الثانوي | مسؤول النظام (System Administrator) |
| الهدف | البحث عن الطلبات باستخدام معايير تصفية محددة. |
| المتطلبات المرتبطة | FR-023 |
| الأولوية | متوسطة |

## معايير البحث المقترحة

- Request ID
- الحالة (Status)
- نوع الطلب
- الأولوية
- تاريخ الإنشاء
- النظام العميل
- نتيجة التنفيذ

## التدفق الأساسي

1. يحدد Actor معايير البحث.
2. يرسل طلب البحث.
3. يتحقق النظام من صحة المعايير.
4. يطبق النظام الصلاحيات.
5. يبحث النظام في الطلبات.
6. يرتب النتائج.
7. يقسم النتائج إلى صفحات (Pagination).
8. يعيد النتائج إلى Actor.

## التدفقات البديلة

### A1 – لا توجد نتائج

يعيد النظام قائمة فارغة مع معلومات Pagination.

### A2 – معايير بحث غير صالحة

يرفض النظام الطلب ويعيد سبب الخطأ.

## الشروط اللاحقة

- لا تتغير بيانات الطلبات.
- يعرض النظام فقط الطلبات المسموح للـActor برؤيتها.

# 7. UC-005 – مراقبة صحة النظام  
## Monitor System Health

| الحقل | القيمة |
|---|---|
| المعرف | UC-005 |
| الاسم | مراقبة صحة النظام (Monitor System Health) |
| Actor الأساسي | مسؤول النظام (System Administrator) |
| Actor الثانوي | منصة المراقبة (Monitoring Platform) |
| الهدف | التحقق من الحالة التشغيلية لخدمات النظام ومكوناته. |
| المتطلبات المرتبطة | FR-024، FR-025 |
| الأولوية | عالية |

## التدفق الأساسي

1. تطلب منصة المراقبة أو مسؤول النظام بيانات Health Check.
2. يجمع النظام حالة الخدمات.
3. يتحقق النظام من الاتصال بقاعدة البيانات.
4. يتحقق النظام من الاتصال بـRabbitMQ.
5. يتحقق النظام من حالة الخدمات الأساسية.
6. يعرض النظام الحالة الإجمالية والتفاصيل.

## الحالات الصحية

- `UP`
- `DEGRADED`
- `DOWN`
- `UNKNOWN`

## التدفقات البديلة

### A1 – خدمة غير متاحة

1. يحدد النظام الخدمة المتأثرة.
2. يغيّر الحالة الإجمالية إلى `DEGRADED` أو `DOWN`.
3. يرسل بيانات الحالة إلى Monitoring Platform.

## الشروط اللاحقة

- تكون حالة الخدمات متاحة للمراقبة.
- يمكن تسجيل أو إرسال تنبيه عند اكتشاف عطل.

# 11. UC-009 – إدارة إعدادات النظام  
## Manage Configuration

| الحقل | القيمة |
|---|---|
| المعرف | UC-009 |
| Actor الأساسي | مسؤول النظام (System Administrator) |
| الهدف | عرض أو تعديل الإعدادات التشغيلية المسموح بتغييرها. |
| المتطلبات المرتبطة | متطلب وظيفي إضافي مقترح |
| الأولوية | متوسطة |

## الإعدادات الممكنة

- الحد الأقصى لمحاولات Retry
- فترات Retry Delay
- حدود Rate Limiting
- أولويات الطلبات
- Queue Mapping
- حدود Timeout
- تفعيل أو تعطيل أنواع طلبات محددة

## التدفق الأساسي

1. يطلب المسؤول عرض الإعدادات.
2. يعرض النظام القيم الحالية.
3. يختار المسؤول إعدادًا للتعديل.
4. يتحقق النظام من صحة القيمة الجديدة.
5. يحفظ النظام التعديل.
6. يسجل النظام العملية في Audit Log.
7. يطبق النظام الإعداد الجديد.

## التدفقات البديلة

### A1 – قيمة غير صحيحة

يرفض النظام القيمة الجديدة ويعرض سبب الرفض.

### A2 – الإعداد يتطلب إعادة تشغيل

يحفظ النظام القيمة ويوضح أن تطبيقها يتطلب إعادة تشغيل الخدمة.
